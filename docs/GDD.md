## 0. 阅读和使用规则

### 0.1 人类确认的四条开发原则（强制）

以下四条由用户于 2026-10-16 明确要求，适用于今后所有任务；不把本文件其他“建议”自动升格为已定规则。

1. **一个任务只包含一个可验证的目标。** 不要让 Codex 一次完成“战斗系统 + 商店 + 羁绊 + UI”。应拆成例如“实现部署费用扣除与不足费用时禁止部署”，并明确验收标准。如果违反这一准则，必须拒绝任务并提示拆分，除非人类明确发出认可指令。必要的文档、测试、Git 提交和交付说明服务于同一个目标，不作为扩展玩法的理由。
2. **每个任务先阅读相关文档。** 文档是设计依据，不根据上次聊天猜测规则。先读根目录 `AGENTS.md`、`docs/STATUS.md`、当前任务卡及本圣经相关章节，再检查实际文件和 Git 状态。
3. **每完成一个可运行功能就提交 Git。** Unity 的场景、Prefab、`.meta` 文件都必须正确纳入版本控制；`Library`、`Temp`、日志等缓存不提交。提交前运行相关验证；未运行或失败必须如实记录。本地提交不自动授权远端推送和发布。
4. **必须提供测试证据与系统连接说明。** 每次交付告诉人类改了哪些文件、做了什么测试、哪些测试没能执行、还存在什么风险，不能只回复“已完成”。每次额外解释新增的关键类、核心接口和数据流；人类不需要逐行理解所有代码，但必须知道系统如何连接。没有新增类或接口时明确写明。

## 3. 三条设计支柱与验证问题

1. **构筑有价值。** 换阵容、升星和羁绊能改变进攻办法；不能只比较总战力数字。
2. **操作有价值。** 同一阵容通过部署间隔、路线选择、技能时机，可以产生可观察的结果差异。
3. **信息可推理。** 玩家能提前看懂敌方威胁、路径、费用、次数和冷却；失败后知道下一次可以改什么。

首个原型只回答一个核心问题：**在无自然回费、无倒计时的前提下，有限资源下的部署顺序和技能时机，是否足够形成有意思的选择？**

如果答案是否定的，先调整防守互动、阻挡关系和单位分工；不要靠添加更多卡牌掩盖核心问题。

## 4. 核心循环与流程边界（建议）

### 4.1 玩家的重复行动

```text
观察下一关防守与路线
        ↓
用招募金币购买 / 刷新 → 合成升星 → 调整编队 → 查看同时激活的羁绊
        ↓
锁定本场编队与羁绊，获得本场战斗费用及部署次数
        ↓
观察防守动作 → 选择路线、卡牌、时机 → 扣费并生成怪物
        ↑                                      ↓
重新判断资源 ← 技能回费 / 冷却结束 / 击杀反馈 ← 移动、阻挡、攻击、技能
                                               ↓
                                    怪物穿门 → 防御值下降
                                               ↓
成功 → 获得金币 → 下一关招募；最终关成功 → 通关 → 开始新挑战
失败 / 主动放弃 → 看到原因 → 重试本场，或返回新挑战
```

随机商店是构筑的一部分；不附加肉鸽事件系统。防守方由关卡作者预置，不实现对手自走棋运营 AI。

### 4.2 短流程结构

建议课程基础版为 3 场关卡组成的一次挑战，每场前有一次商店准备。金币和收藏跨场保留，战斗费用与卡牌部署状态每场重置；新挑战重置本次构筑。失败后可用相同开战快照重试，或新开挑战。重试不额外送钱、不刷新商店、不重掷战斗种子，避免通过重试刷资源。

不做局外永久属性成长、联网、账号、玩家对战、赛季、装备系统和完整长篇剧情。存档先保存关间进度；战斗中断点续玩属于后续项。

## 5. 已确认的六项核心规则（2026-10-16）

| 编号 | 问题 | 已定方案 | 原因 / 验证办法 |
| --- | --- | --- | --- |
| D01 | 无费时是否立刻失败？ | 场上结算完且不存在可恢复的部署机会后才资源耗尽失败 | 防止最后一个进门怪物、回费技能、冷却中的低费卡被误判 |
| D02 | 怎样从容思考？ | 战前无限观察；战中提供战术暂停，暂停可选牌与预览，恢复后才正式提交部署 / 技能 | 与实时部署相容；验证是否过于繁琐；不默认允许无限队列 |
| D03 | 羁绊按什么计数？ | 按开战前编队中的不同怪物种类计数，固定本场羁绊等级；是否部署、部署次数、死亡和穿门均不改变 | 不按场上存活实体动态变化；备战不计，同种重复卡去重 |
| D04 | 次数、升星怎样结算？ | 每张编队卡独立保存本场次数，每场重置；三张同种 1 星合 2 星，三张同种 2 星合 3 星，最高 3 星 | 各星部署次数和属性仍按单位配置另定，不推出全员相同成长公式 |
| D05 | 首领技能属于谁？ | 每个已部署首领实体有自己的技能 CD；从首领头像选择实体释放 | 允许多首领，避免一个冷却覆盖全部同名首领 |
| D06 | 回费能否无限循环？ | 暂不设置本场累计回费上限；仍需满足施放条件与独立技能 CD，不产生自然回费 | 存活首领可能重复回费；允许战斗持续，不能因旧预算假设判负或偷偷超时失败 |

以上规则来自用户本次明确回复，覆盖此前相冲突的草案。D02 采用此前完整提案：暂停可选牌与预览，恢复后才能执行部署/技能；不额外引入指令队列。D05 的初始 CD 数值、各星成长、升级经验与金币仍待确定。随后用户已确认商店概率、刷新/出售返库及缺货规则，见第 7 节。

## 6. 战斗规则规范（建议）

### 6.1 资源与卡牌状态

两种货币完全分离：`Gold` 为招募金币，只用于战间商店；`DP` 为本场战斗费用，只用于部署和明确标价的战斗行为。原型主动技能默认不消耗 DP，避免第一轮把所有交互耦合起来。

每个编队卡实例包含 `cardInstanceId`、`unitId`、星级、部署费用、剩余次数、下次可部署时刻。`部署次数` 指“成功执行部署命令”的次数；一张群体卡生成多个实体，也只扣一次部署次数。实体另有 `entityId`，保存当前血量、位置、目标和技能状态。

本场初始化：`DP = initialDP`；卡牌次数由配置与星级计算；部署 CD 初始为就绪。死亡和穿门不会默认返费，也不会返还次数。穿门实体立即离场。原型不支持撤回返费。

部署必须同时满足：战斗正在进行、费用足够、次数大于零、该卡冷却完成、入口 / 路线合法、生成点可用。失败请求返回可读原因，**不扣费、不扣次数、不进入冷却**。成功请求作为一个原子操作完成扣费、扣次数、设置 CD 和生成命令；快速连点也不能只扣一次却生成两次。

不设置首领专属并发上限。若需要防止单位重叠，使用短暂生成排队或入口位置检查；若设备压力需要总实体预算，先通过内容与对象复用控制，再由负责人决定，不能借性能名义加入首领配额。

### 6.2 时钟、暂停与信息

使用统一战斗模拟时钟驱动移动、攻击、部署 CD 和技能 CD。战术暂停、菜单暂停、失去焦点是否暂停须统一配置；建议课程版失焦即暂停。暂停时所有战斗逻辑冻结，不允许挂在暂停页等回费或冷却。

正常速度 1×；2× 为有余量再加的功能。加速影响整个模拟时钟，不分别乘某些动画。不得用系统现实时间推进暂停中的战斗 CD。技能施放特效是表现，伤害 / 回费结算由逻辑事件负责。

### 6.3 路线、阻挡、攻击

建议采用固定路点路线，原型不需要动态寻路或物理碰撞决定阻挡。怪物沿路线前进；进入防守者接战范围时，依规则占用其阻挡容量，被阻挡者停下攻击，未占用阻挡名额者继续走。

首版地面单位被阻挡会还击，防守方拥有固定射程、攻击间隔、阻挡数与生命。防守者被击杀会永久离场，直到本场重试。没有飞行、隐身、召唤套召唤、动态改路和多层仇恨。

同一距离有多个目标时，按稳定的“路径进度优先，再实体 ID”规则选取；死亡立即释放阻挡名额。最终顺序在技术记录中固定，避免执行次序每帧漂移。

可采用最小伤害公式 `max(1, attack - armor)`；所有单位使用同一基础伤害类型，复杂抗性暂后置。不要先实现多套伤害体系。

### 6.4 蓝门结算

单位第一次完成路线时产生唯一穿门事件：`defense = max(0, defense - gateDamage)`，随后销毁或回收实体。相同事件 ID 只能处理一次。较强单位允许有更高 `gateDamage`；召唤物、群体卡每个成员分别配置，防止一张卡意外造成成倍穿门伤害。

同一模拟步内先按已经确定的死亡 / 移动规则产生活体穿门事件，再结算防御值，检查胜利，最后检查资源耗尽。已在本步死亡的单位不能继续穿门。胜利成立后锁定状态，不再触发失败、重复奖励或延迟技能回调。

### 6.5 胜负、回费和死局

胜利条件：防御值降至 0。基础失败条件保留用户意图：**进攻资源耗尽，已经无法再组织进攻。** 不能实现为“当前 DP 小于最低费用就立刻失败”。

按照 D01 已确认的保守规则，按以下顺序判断：

1. 若已进入胜利 / 失败 / 主动放弃状态，不重复判定。
2. 若蓝门防御值为 0，胜利优先。
3. 若仍有场上进攻单位、待生成单位或待结算事件，继续运行：它们可能进门、击杀或触发回费。
4. 若没有以上内容，但存在“剩余次数 > 0、DP 足够”的合法卡，允许等待其 CD 或入口恢复，不判负。
5. 若本场存在已经承诺、将在未来结算的回费事件，先等待。主动回费若依赖首领，首领死亡后不能再假定它会施放。
6. 在场上清空、事件清空、无可恢复机会后，进入资源耗尽失败；显示 DP、剩余次数与原因。

“等待机会”不等于求解所有未来策略。基础内容限制下，空场时只有部署 CD、入口恢复和登记在案的延迟事件可等待，因此可保守、可靠地实现。以后添加全局回费、复活、召唤等机制时，必须同时扩展这个判定。

永久阻挡、零伤害互殴、无限治疗或可重复回费可能造成场上长期不清空。先用最低伤害、单位交互与内容验证检查死局；D06 暂不设回费累计上限，不得用旧草案偷偷补回限制。保留主动放弃、重试；长时间无进展只能提示，**不偷偷转成超时失败**。调试看门狗只输出异常信息。

| 场景 | 正确结果 |
| --- | --- |
| DP 为 0，最后一只怪正在走向蓝门 | 继续，可能获胜 |
| DP 足够，唯一可用卡还有 5 秒 CD | 继续，CD 到点可部署 |
| 没钱，首领在场且回费技能将就绪 | 继续，能施放后再判断；不假设存在累计回费预算 |
| 空场，有钱，但所有卡次数用完 | 失败 |
| 空场，无钱、无事件、无回费来源 | 失败 |
| 本步穿门使防御值为 0，同时 DP 耗尽 | 胜利，奖励只发一次 |
| 暂停 30 秒后恢复 | CD、路径和回费量均不因现实等待而变化 |
| 两个首领同时存在 | 各自技能与头像正确；没有隐含首领上限 |
| 费用恰好够，连点两次 | 只有通过验证的命令生效，不出现负费用 |
| 强制重试 | 血量、阻挡、CD、次数、随机种子与快照正确恢复 |

## 7. 招募、升星、编队与羁绊（已定规则与待定参数分别标记）

### 7.1 商店

**已定：** 每次刷新提供五个购买位；招募费用分为 1–5 费；每种怪物初始固定 9 张基础牌，拥有该怪物的牌会减少其可抽库存。等级 1–10，采用 [SHOP-v0.1 的十级费用档概率表](proposals/SHOP-v0.1.md)，用户已逐项确认；不再采用按三场分别抽 1/2/3 档的旧表。

招募费表示商店档位/购买金币，与战斗部署 DP 分开配置；不把“5 费怪物”解释为战斗部署一定消耗 5 DP。首领通常较贵且难抽，但不是额外首领配额。

**已定的抽取与库存规则：** 每槽先按等级抽费用档，再按该档剩余基础牌数加权抽取；展示牌占用库存，避免同一刷新超抽。未购买牌在刷新时返库；出售 1/2/3 星分别返库 1/3/9 张，返库数不等于售出金币数。某费用档抽空后，只在本等级基础概率大于 0 且仍有库存的档中按原概率比例归一化，不解锁高费档。合法库存不足五张时只展示实际可抽数量并提示缺货，空槽不能购买。详细算式与边界见 SHOP-v0.1；这些是已确认设计，尚未实现或写入运行配置。

**仍是试验建议：** 开局 8 金币、刷新 1 金币、每场成功奖励 6；买卖/刷新仅准备阶段，新一轮自动刷新一次。售出金币金额、升级途径/经验/花费/开局等级、备战格数及金币收益均未确认。参考概率不等于一并采用原作的利息、装备、投资策略或经济数值。

牌库按基础牌等价数记账：拥有 1 张 2 星占 3 张库存，1 张 3 星占 9 张；合成不凭空返库。持有某种怪物的 3 星就占满其全部 9 张，在仍持有期间不能再抽到该怪物。部署产生的战斗实体不是新的商店卡，不额外扣牌库；死亡/穿门不归还持有的卡。各怪物须满足 `可抽库存 + 商店占用 + 持有基础牌等价数 = 9`；购买把商店占用转入持有，不重复扣库存。

### 7.2 合成与编队

**已定：** 三张同种 1 星合成一张 2 星，三张同种 2 星合成一张 3 星，上限 3 星，不存在 4 星。每张编队卡独立保存部署次数/CD，每场重置；同名卡可同时编队。各星属性与部署次数增量尚待单位配置确认，不能自动套用统一公式。

**已定：** 等级 1–10，战前编队卡槽上限等于等级；不是战场实体数上限，战场可同时有多批已部署单位。所有编队槽都可放首领，只要招募和费用允许。**建议：** 备战暂为 6 格，仍待确认。备战满时先检查购买是否会即时合成腾位，完整事务成功才扣金币；合成后位置与连续升星的事务顺序在实现前明确。

同名卡可以同时编队，各有独立次数和部署 CD；羁绊计数时按种类去重。上场阵容锁定后，本场不能购买、出售、升星或修改羁绊快照。

### 7.3 羁绊和流派

“标签”是单位身份；“流派”是玩家通过标签、单位技能与部署节奏形成的作战方法。每种怪物可有多个标签，全部参与统计；某单位拥有 A、B 两标签，就同时为 A 与 B 各贡献一种。

建议基础版 3 组羁绊，阈值 2 / 3；按最高达成档位生效，低档是否累加必须在配置中写明，基础版不叠加低档数值。以下为机制草案，名称为占位：

| 标签 | 2 种效果草案 | 3 种效果草案 | 产生的玩法 |
| --- | --- | --- | --- |
| 集群 | 该标签小怪增加一次部署 | 再缩短该标签部署 CD | 多批进攻，拉开或压缩到达间隔 |
| 破阵 | 该标签对防守者的伤害提高 | 首次接战附带一次削甲 | 主动拆除阻挡，再送高穿门伤害单位 |
| 协同 | 首领首次施放后，后续一批小怪短暂减伤 | 减伤覆盖更大范围或多一次触发 | 首领先创造窗口，小怪随后推进 |

不把回费放进第一版羁绊，先单独验证资源闭环。效果可改，但每个羁绊至少应改变一项部署或技能选择，不能三组都只有相同的攻击加成。

**计数例：** 编队甲[A,B]、乙[A,C]、丙[B,C]、丁[A,B]，则 A=3、B=3、C=2；三组同时生效。甲部署三次仍只按一种计数。备战卡不计数，同名甲再上场不额外加种类。

### 8.3 课程基础版内容职责草案

六种小怪建议覆盖：快速穿门、抗伤、拆阻挡、群体部署、远程支援、条件强化。两名首领建议分别覆盖：主动回费、创造突进窗口。第一轮只保留必需效果，不为凑数量写八套独立框架。

## 9. UI、反馈、美术与音频（建议）

准备界面必须同时看见金币、商店、编队、备战、星级、标签、激活档位与下一关防守预览。点选卡牌可查看每次生成数、整场次数、部署费、部署 CD 和技能描述。

战斗界面持续显示：剩余 DP、蓝门防御、每张卡剩余次数 / 冷却、首领实体头像与技能状态、暂停、主动放弃 / 重试。禁用卡显示具体原因；玩家应能区分缺费用、次数耗尽、冷却中和入口非法。

部署使用“选卡 → 选入口 / 路线 → 确认”，提供取消与路线预览。先做清楚的点击交互，再决定是否增加拖放。右键 / Esc 取消选择的行为不能与暂停冲突。场上首领可通过头像定位。

原型用几何形状和清晰轮廓区分角色。正式风格待确认；先统一尺寸、颜色、朝向、动画节奏、图标含义。护盾、阻挡、范围技能与穿门要有可见反馈；重要状态不能只靠颜色区分。字体必须包含实际使用的中文字符。

音频先覆盖部署成功、不可部署、技能、穿门、胜负五类；加入总音量与静音。持续音效控制叠加数量。美术和音频来源逐项记录；正式版尽量使用原创名称、轮廓和文字，把参考作品的战术功能转成自己的实现。是否使用原作具体素材、角色或背景另行确认，不默认已经取得可用资源。

## 10. 运气与操作的平衡验证

目标拆开验证：

- 商店随机不应让一场正常教学关失去任何可执行方案。建议保底起始基础卡，并让低稀有度单位能覆盖抗伤、拆阵等必要职责。
- 在指定“弱阵容”测试快照中，较好的部署 / 技能操作能明显改善穿门结果；不声称所有弱阵容都能过所有关。
- 强构筑可以降低操作要求，但不应靠伤害数字遮住信息，让玩家不知道为什么变强。

每轮先做 3 个固定种子的普通阵容快照、2 个较弱快照、1 个强阵容快照。比较三种行为：随意点卡、按基础战术部署、较熟练地把握首领技能。记录胜负、剩余防御、费用利用、无效操作和等待时间；胜率不能替代玩家说明。

建议第一次请 3–5 位未参与设计的人试玩，记录是否能独立开始、是否看懂失败原因、是否提出另一种部署尝试。样本只能提供问题线索，不能据此宣称总体平衡。

如果所有测试都只需要开局把卡点完：增加需要分批处理的阻挡 / 伤害窗口。如果主要时间是在等 CD：缩短冷却、优化批次并提供加速；不要强加倒计时。若羁绊永远只有一套最优解：比较同预算的不同组合与关卡对局，不先增加标签数。

## 11. 数据与实现边界（建议）

配置数据与运行状态分开。配置可采用 ScriptableObject，运行时复制到状态对象，不直接修改配置资产。稳定 ID 用于卡牌引用、关卡配置、存档与日志，不依赖中文显示名。

| 数据 | 最小字段 |
| --- | --- |
| UnitDefinition | unitId、显示名、定位、是否首领、商店档位 / 买价、部署费、各星次数、部署 CD、每次生成数、HP、攻击、护甲、移速、穿门伤害、标签、技能 ID |
| SkillDefinition | skillId、目标规则、初始 CD、后续 CD、效果、失去目标处理；D06 当前无累计回费上限，不要求预算字段 |
| SynergyDefinition | synergyId、阈值列表、是否累加、适用对象、效果与展示文字 |
| LevelDefinition | levelId、初始 DP、防御值、路线、防守配置、奖励、开战提示 |
| CardState | cardInstanceId、unitId、星级、剩余次数、部署可用时刻 |
| UnitState | entityId、来源卡实例、HP、路线进度、阻挡者、技能可用时刻、累计回费 |
| RunState | 存档版本、种子 / 随机状态、金币、等级/经验、收藏、编队、当前场次、商店占用与各怪物剩余基础牌数、开战快照；数据结构尚未实现 |

核心战斗逻辑尽量为可测试的普通 C#；Unity 组件负责输入、显示、场景引用、音效与对象生命周期。先使用少量直接接口，避免全局服务容器、大型行为树、ECS 或通用技能语言。

配置校验必须发现：重复 ID、缺失引用、负成本、无效路线、同卡标签重复、概率不归一、技能预算与结束判定不兼容。原型重复快照测试要求同一版本、同一操作序列产生稳定结果；不承诺跨平台逐帧完全确定。

## 12. 课程交付验收（建议）

功能：从启动到三场挑战结算可完整运行，失败可重试，新挑战可重开；商店、升星、同时生效的羁绊、部署次数、独立 CD、蓝门伤害均可现场演示。

稳定性：没有阻止完成流程的已知故障；发布包不依赖 Unity 编辑器；从干净目录打开工程能重建；第二台电脑实测启动；存档损坏有明确恢复入口。帧率目标先在负责人实际电脑上记录，建议基础目标为 1080p、正常课程场景平均 60 FPS，并同时检查卡顿峰值；它是待测目标，不是当前成绩。

体验：新玩家能看懂至少一种羁绊、一次技能窗口和一次失败原因；至少留下一组“相同阵容，不同操作产生不同结果”的录像或数据。没有证据时不写“已经验证好玩”。
