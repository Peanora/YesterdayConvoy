# 固定战场布阵战斗

2026-11-17。用户已确定的新战斗方向，作为后续常规玩法开发基础；优先级见 [GDD 顶部规则](GDD.md)。本页分别记录用户已定规则、基础 Demo 的实现约定与尚未验证的体验目标，不能用旧路线战斗的通过记录证明本模式已通过。

## 用户已定的战斗闭环

1. 一次挑战使用同一张清晰的矩形地图。左半边为我方怪物的战前部署区，右半边展示需要进攻的守军干员。
2. 玩家在左半边自由选择多个格点站位。阵容和站位跨关保留，后续准备阶段在原阵容上购买、升星、替换或换位。
3. 每关守军随机，并随进度变得更强。本关敌阵在准备阶段完整公开，玩家看过后开始战斗。
4. 开战后我方自动接敌、攻击和释放技能，战中不再拖卡出兵或手动施放技能。
5. 我方角色阵亡后有复活等待时间，结束后从本场原部署位置自动再次进攻。
6. 每关有时间限制。伤害不足或阵容过脆、频繁复活都可能导致无法通关。
7. **必须先消灭所有守军，我方才会向蓝门前进；之后至少一名存活我方角色实际进入蓝门才算胜利。** 不能绕过守军进门获胜，也不能在清场瞬间提前结算胜利。

主要循环为：**准备与布阵 → 自动战斗／阵亡复活 → 清空守军 → 自动进门 → 结算与下一关准备**。

招募、升星和羁绊仍是主要成长方向；玩家卡池仍以已确认的怪物及指定特例为准，守方仍统一为可以被消灭的干员。不因参考其他自走棋而自动引入装备、遗物、肉鸽或新角色类别。

## 与旧战斗的关系

新常规战斗不再沿用红门拖卡生成、逐波费用分配、反复手动部署、曲折固定路线和手动开技。新方案明确采用限时挑战，并以“全歼后进门”取代旧版可绕过存活守军穿门扣尽防御的胜利路径。

未迁移的旧关卡、角色测试和专项暂时保留各自运行行为，便于继续查看与回归；它们属于旧模式或专项样板，不能反向覆盖本页的新设计基线。本轮已接入既有商店的真实交易与编队／备战席位；完整卡池、羁绊及原作复杂角色机制仍需逐项迁移与验证，不把基础 Demo 等同全游戏改造完成。

## 首轮实现约定与待调整边界

下列为让 Demo 可以运行和试玩的实现决策，**不登记为用户最终数值或已完成的人类验收**。

| 项目 | 首轮实现约定 |
| --- | --- |
| 关卡计时 | 采用整个关卡的统一模拟时限，包含复活等待、返场与清场后进门；清场后留有短而清楚的进门过程 |
| 守军行为 | 守军在生成位置固守，阵亡后本关不复活；未死亡守军保留伤势，治疗按本模式的实际能力结算 |
| 我方复活 | 每张上阵卡只对应一个本体；阵亡后等待，满血回原格，不额外复制卡牌或占用商店库存 |
| 复活与技能 | 保留本场技能进度／冷却，复活不重新领取首次登场收益；避免故意送死刷新技能优于正常存活 |
| 暂时全灭 | 有剩余时间且仍可复活时继续战斗，不因场上暂时无人立即判负 |
| 超时 | 未完成“清场且至少一名本体进门”则失败，结算只执行一次 |
| 战前布阵 | 左侧合法空格可移动，占位可交换；非法释放／取消不改阵容；开战后锁定部署格，复活读取该锁定位置 |
| 随机守军 | 只在准备阶段生成本关阵容；同一关战斗中不重抽，同关重试保留该敌阵与我方编排。数量、面板与特殊能力分开控制，避免同时无约束增长 |
| 模拟时钟 | 暂停冻结移动、攻击、技能、复活和关卡倒计时；倍速对同一模拟时钟生效 |

复杂角色的召唤物是否计入清场、原生多阶段复起与本模式复活如何衔接、死亡收益的重复触发边界，须在相应角色迁移时明确并验证。本基础 Demo 不借简化技能样板替这些角色作出最终决定。

## 基础 Demo 范围

角色资源沿用工程既有来源和权利记录，本轮没有改绘角色或新增外部角色素材。用户确认最新暖灰工业棋盘概念图后要求接入：继续采用 14×8 矩形棋盘，左侧开放布阵，右侧加入两处高台和两处低掩体；完整透明红蓝门、工业外围和原 A 商店保留。地面改为偏暖灰、细颗粒、低反光的旧混凝土，以窄缝和轻微磨边读格，覆盖此前原材质明暗交替、道路白短线与米金光泽方案。此前 LS-5 窄通道预览只用于核验美术，不取消矩形布阵规则；旧 AI 庭院背景投影和方块重建也不作为当前依据。新挑战更换守军随机种子并重置商店会话，同关重试保持本关守军与已经购买的卡牌，便于比较布阵和升星。

地图为独立保存的 `Assets/Scenes/FormationBattle.unity`。地形、分区、蓝门与必要材质在编辑模式可见、可编辑并保存；运行时只创建本关角色、交互与反馈，不重新搭建整张地形。

Unity 菜单 `Yesterday Convoy → Formation Battle → Create Missing Scene` 仅在场景缺失时创建基础地图，不重写已存在场景中的人工编辑。本轮作者入口为 `FormationReferenceMapTools.Apply()`／`Validate()`，菜单 `Apply Approved Concrete Battlefield`／`Validate Concrete Battlefield`；它在原资源导入基础上保存混凝土棋盘、地形和工业装饰。单独执行旧 `FormationNativeMapTools.Apply()` 只会得到较早的原资源重排底图，不是本轮完整接入。编辑范围见下方地图说明；各版本实际校验、测试与 Windows 构建结果由 STATUS／QA 记录。

上述起始资源、五关时限和强度属于短流程试玩初值。商店接入使用真实金钱与库存事务，**不因此证明自然获卡概率、完整运营可达性或整体平衡已通过**；基础模型保留的免费升星／扩编方法仅供既有专项测试，不作为本轮玩家整备入口。

地形坐标使用棋盘列／行，起点是占地矩形的左下格。高台允许守军站立，生成守军时优先给远程角色分配高台，近战优先地面；掩体不生成守军。我方绕过四处固定占地轮廓接敌，允许到台边按原有平面距离近战攻击高台守军，清场后同样绕行进蓝门。高度用于角色和地形的显示，不增加高地免疫、减伤、额外射程、掩体破坏或视线判定；不能把高台显示误写成只能远程攻击的目标。

角色复用工程已有美术与动作，攻防和自动技能采用本模式的小范围样板：重装防御者短时防护、猎狗突袭、士兵强化、弩手连射、术师范围法伤、传令兵治疗。这些能力只用于验证本模式的承伤、输出和支援关系，与旧战斗中完整原作技能的实现不同；后续须按角色逐项迁移，不宣称本 Demo 已完整移植全部原作技能、天赋和特效。新地图为用于验证站位与接敌的基础战场，不把它登记为最终地图美术验收通过。

## 真实商店与军阵

本轮商店复用 `ShopTrialModel` 的五格商品、费用解锁概率、分费用有限牌库、刷新返库、售出返库、锁店、经验与结算事务；`ShopSeatLayout` 管理上阵席位和十格备战，`FormationShopSession` 将选中的真实卡实例导入本模式。没有启动旧 `ManualBattleController` 或旧路线战斗来代替新战场。

界面直接复用 `ApprovedShopPresentation`／`ApprovedUi` 的原 A 共享实现：Market 商品面板、真实 idle 模型的 RenderTexture 平台、购买入场／合成 Flow、金币等级与经验；上阵槽 y=516、备战槽 y=627 沿用原几何。不是在本模式重新画一套近似 UI，也不以静态卡面代替平台角色待机。UI 只回调本模式会话，不复制经济或战斗状态；原 A 的实机观感与交互仍须本轮运行核对。

- 合成优先保留已经上阵的卡实例与原站位；同种换入实例时保留该种类最近站位。删除或出售角色后不保留无卡实体，备战角色不生成战场本体；复活不新增库存占用。

金币、库存、卡实例、席位与站位跨关保留；全新挑战才重置会话。战斗、复活与清场进门期间禁止购买、刷新、卖出、换编队或买经验；整备页面的真实交易不能被免费升星／扩编入口替代。卡面沿用的标签用于角色识别，本模式尚未结算对应羁绊；完整原作技能和其他卡种也尚未迁移。

## 入口与操作

- 直接打开 `Builds/Windows/YesterdayConvoy.exe`，默认仍是原挑战；本轮显眼入口为默认行动准备阶段的“战前布阵 · 新玩法试玩 ▶”。右上角菜单“矩形攻坚 · 新玩法 Demo”别名继续保留，也可传入 `-formationDemo` 直接进入，不提供额外启动脚本。入口实际显示与跳转结果由本轮 Player 验证记录。
- Unity 中打开 `Assets/Scenes/FormationBattle.unity` 后 Play，可直接进入本模式。
- 准备阶段点击顶部五格商品购买，卡牌进入备战；Tab 或右上按钮开合原 A 商店，右侧可花 2 金币刷新或锁店，并提供“买经验 4金币”。金币、等级与经验沿用共享原 A 资源显示。
- 底部上阵／备战各有十个席位，上阵位按当前等级解锁。拖动卡牌可换位或交换实例；同名仍只允许一张上阵。需要升星时购买同种卡触发三合一，不再使用免费体验按钮。
- 可将备战卡拖到左侧合法地图格直接加入军阵，前提是有空人口且不重复同名；也可选中已经上阵的卡再点击合法格，或拖动场上角色换格。落在我方占用格时交换位置，落在右侧等非法区域时保留原编排；场上角色可拖回备战。
- 拖动卡牌或场上角色时，战场左右边缘显示“松开出售”及真实售价；松开到该目标会卖出卡实例、入账金币并按星级返库，普通换格应避开出售目标。
- 点击开始后自动交战与释放技能，战中不修改布阵；原部署格保留，死亡后自动复活返场。空格切换暂停，界面可切换 1×／2×速度。
- 同关重试保留我方阵容、星级和站位，也保留该关已公开的守军，不通过反复重试抽换敌阵。进入下一关后继续使用同一张地图和我方编排。

## 数据与运行连接

`FormationBattleModel` 唯一持有本模式的战斗规则与运行状态，处理布阵、随机守军、移动索敌、攻击和自动技、伤害治疗、复活、统一计时与胜负结算。准备期通过 `ApplyRoster(entries, capacity)` 导入真实上阵卡实例、星级与部署格；战斗不扣除招募金币或消费额外卡牌。

`FormationShopSession` 持有本次五关会话的 `ShopTrialModel` 与 `ShopSeatLayout`。`ApplyTo` 导入编队，`SavePositions` 保存实例／同种站位；购买、刷新、买经验、出售和换席包装负责准备期限制与交易后的席位同步。`SettleWin` 按关号只结算一次，`AdvanceRound` 与 `Retry` 统一推进绑定的战斗模型，调用方不重复推进关卡或刷新商店。

`FormationBattleController` 读取模型，负责现有角色美术的表现与输入连接；`FormationBattleInterface` 是同一个 Controller 的界面部分，展示状态并把操作交给模型。`FormationShopMarket` 通过 Host 回调直接使用共享 `ApprovedShopPresentation` 的 Market、idle RT 平台和 Flow，将商品点击、拖放、出售、刷新和买经验交给会话；上阵／备战矩形直接读取 `ApprovedUi`，不另外维护战斗计时、卡牌库存或伤害结算。

场景中的 `FormationBattleTerrainAuthoring` 保存四处地形的格占地、高度和守军许可。Controller 启动时调用 `BuildLayout()`，复制为只读的 `FormationBattleTerrainLayout` 交给模型；它在初始化时预计算固定轮廓角点连接，战斗只查询这些轮廓完成绕行、台边接敌和进门，不依赖运行时搭图或场景物理碰撞。`ActorWorldPoint` 读取相同布局的高度显示角色，攻击距离仍使用原平面规则。

`FormationBattleTools` 仅在 Editor 中创建缺失的保存场景、材质与地形，并校验引用。运行时从已保存场景开始，不使用这个工具重建地图，也不覆盖人工保存的场景。

`FormationNativeAssetTools.EnsureImported` 导入保存原部件 Mesh、贴图与材质，不改场景；`FormationNativeMapTools` 提供112格、原工业部件和16门的底层重排，`FormationReferenceMapTools.Apply` 在此基础上保存本轮混凝土地形与围合装饰，`Validate` 检查材质、四处地形、门位与相机范围。工具不在 Play 中执行，实际执行与画面核对结果由 STATUS／QA 另记。先前 Industrial／Painted 环境不再是本轮编辑依据。

## 成长与战斗反馈目标

- 同类守军可以作为稳定标尺：成长后能够更快消灭熟悉的基础守军，关键技能有清楚的命中、扣血和连续击倒。
- 前排承伤、远程输出和支援覆盖应真正受站位影响；不能让所有角色开局立刻挤成一团，从而抹掉布阵差异。
- 显示剩余守军、关卡剩余时间、我方复活等待和真实角色贡献，使玩家能理解输出不足与频繁阵亡的区别。
- 守军总数与同时有效集火人数分开控制；数量增多不等于所有守军同时攻击我方。
- 随机关卡应允许沿用主要阵型，针对性小调整能够改善结果；地图固定不能被“每关彻底重抽强克制阵容”抵消。

这些是待验证目标。固定高星样板通关、自动模拟获胜和人类感受到成长属于不同证据，分别记录。

## 验证与后续开发入口

优先验证：准备阶段合法移动／交换与取消、站位跨关继承、技能自动触发、死亡后原位复活、暂停冻结全部计时、守军未清空不进门、清场后仍需实际进门、暂时全灭继续等待、超时失败、重复结算与重开清理。

真实商店还需验证：购买／失败扣费边界、商品与持有卡占库守恒、合成保留实例及站位、一费四星导入、满备战购买合成、出售返库、人口锁与同名限制、战中拒绝交易，以及重试不刷新商品／随机状态或重复领奖。鼠标拖放、商店遮挡、真实idle平台与Flow、原作地砖的格点对应需在实际 Player 中核对，模型交易用例不能代替这部分交互。

成长比较先固定同一敌阵与同一布局，只改变一个关键单位星级；站位比较固定角色和星级，只改变布局。记录实际结果后再判断是否需要调整成长倍率、技能表现或敌方压力。

此前原材质棋盘已有对应版本的构建与验证记录，不能外推为本次混凝土、高台与掩体接入已通过。新地形还需核对守军生成合法性、固定轮廓绕行、近战到台边可攻击、清场后绕行进门、保存场景重试不重建及只读布局一致性。具体构建源码、计数与未测项见[STATUS](STATUS.md)和[QA](QA.md)，程序验证不能代替用户最终观感或完整运营验收。
