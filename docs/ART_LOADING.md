# 角色资源加载与构建

本轮落实菜单轻量读取、按关预加载、离线图集处理和缓存释放，角色造型、动作帧数/时长/尺寸、技能和战斗规则保持。源码和原始运行素材继续随Git交付，不需要队友额外找图或手动传缓存。

## 资源怎样连接

- `ArtCatalog`读取原有JSON，验证身份、必要动作和页面存在性，只保存元数据。`CardDefinition`和`ManualBattleDefinition`的菜单配置校验不再索取完整战斗图；独立卡面沿用原图，M02–M10沿用原待机首帧的透明轮廓裁切。
- `ArtSequence`描述一段动作。菜单头像与动作缓存分开；只有访问动作帧，或明确预加载这段动作时，才准备纹理与Sprite。`LocalMonsterArt`、`DefenderArt`、塔露拉和源石虫原读取接口继续使用，帧播放仍按原模拟时钟。
- `ArtPreparation`在实际菜单入口、BattleShop启动、下一关入口分批准备本关角色；商店只预备当前商品/备战角色的待机。加载页每个图集上传后让出一帧，战斗模拟不推进，完成后才开放正常界面。入口被新的明确操作取代时，旧加载请求取消，不能在稍后覆盖新挑战。
- `ArtMemoryCache`按动作缓存资源，保留本关正/背面动作和备战所需待机。过渡完成后按最近使用顺序释放非活跃资源；描述对象不保留已释放Sprite的强引用，重进角色可安全重建。Unity外部销毁缓存资源时也能重新读取。

缓存目标默认为1GiB，统计使用Unity资源内存估算，并非整个进程RAM或显存上限。**活跃资源优先保护；若本关原始动作工作集已经超过目标，不强行删除屏幕正在使用的资源。** 当前六星防线正背面完整动作本身很大，预加载会出现这种情况。未做降帧/降分辨率，也没有宣称把整场内存硬限在1GiB。之后若仍需降低活跃工作集，应另做按动作预测/流式准备并实际测量。

## 编辑器与EXE

1. Git保留原PNG、JSON及meta；不移动原资源或修改GUID。
2. 编辑器首次Play或构建时，`PreparedArtTools`自动生成`Library/PreparedArt`。首次处理需要等待，后续按源文件内容指纹增量更新；也可用菜单Yesterday Convoy → Art → Prepare Actor Textures提前执行。
3. 处理仍使用原来的Unity纹理压缩质量，只把PNG解码与压缩从游戏中移到准备阶段。缓存保存带尺寸/格式头的预压缩纹理块，再作无损Deflate存储；未对齐压缩块的小卡面保持RGBA。不是新增美术或AI改图。
4. Windows构建自动把派生结果装入Player的StreamingAssets，并仅在**构建副本**中替换对应PNG。项目Assets内原图不删除。运行时直接还原纹理块和上传，不再为这些动画现场解PNG/压缩。
5. `Library`与`Builds`是可重建产物，不加入Git；所有原图和生成工具随源码。队友克隆后自动生成，不存在手工遗漏素材依赖。删Library后首次准备会重做；已打包EXE不需要准备缓存。

编辑器未准备时，兼容入口可回退原PNG读取；正常Player构建应使用派生结果。日志`ART_PREPARE`记录准备时长、预处理页数、PNG回退和缓存估算；回退数用于发现未走优化路径的角色。

## 验收与计时边界

详细结果记录在[QA](QA.md)。基线来自优化前源代码的独立Unity测试进程；最终应再用单独进程运行相同菜单/余全部正面动作基准，避免把之前测试预热的结果当作冷加载。此计时包含测试内场景初始化，不包含启动Unity编辑器、编译脚本或首次离线处理，不等同于任意电脑的EXE启动时间。

相关验证覆盖：菜单不解码战斗动作、预处理资源确实读取、全部帧可取、跨帧进关/暂停、旧加载取消、活跃资源保护、离场释放与重载、原技能/多场景/商店闭环。性能提升只报告实际测到的范围，不据此声称战斗持续帧率问题全部解决。
