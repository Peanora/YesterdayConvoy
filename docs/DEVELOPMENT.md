# 《昨日圆车》开发与 Agent 协作手册

版本：v0.1 · 2026-10-16  
规划基线：剩余 10 周，主导者约 100 小时，两名辅助成员工时另计、不提前透支。  
适用范围：Unity 单人主导的课程游戏；规则以配套 GDD 的“已定 / 建议 / 待定”标记为准。

2026-10-16 修订：引擎已锁定 6000.6.5f1；当前决定以 GDD v0.1-r4 为准。最高 3 星、五格九张有限牌库、1–5 招募费、1–10 级编队槽位及商店概率已定；升级经济仍待确认。以下周计划保持规划性质。

用户现要求前期每次尽量交付一个可玩的完整功能。同一闭环的逻辑、场景、镜头和最小 UI 一起完成；下面 T03/T04 等是参考依赖，可以合并为“一怪一塔、红门进攻蓝门”的 Demo，不再逐项停下等待授权。验证按风险选择，简短更新 STATUS/QA，无需每次新任务卡、证据 JSON、指纹清单或独立审查会话。

## 1. 先明确你承担什么

可以让 Agent 写大部分代码、测试、编辑器工具和文档，但你仍然承担三件不能交给生成结果自行证明的事：决定体验、取舍范围、亲自试玩验收。会不会手写整套代码，不是能不能开始的前提；完全不理解状态与数据，会让后期排错失控。

你最低限度要学会：打开正确 Unity 工程和入口场景；查看 Console 第一条错误；找到卡牌 / 关卡配置；区分场景、Prefab、配置资产和运行状态；查看 Git 改动、提交和恢复；运行测试与构建。每周用约 30–60 分钟复述本周模块的输入、状态、输出和失败方式，这部分计入工时。

不要用“Agent 已完成”作为阶段完成条件。有效证据依次是：规则可说明 → 项目能编译 → 测试运行过 → Unity 中操作符合预期 → 独立构建能运行 → 新玩家能理解并愿意再试。

## 2. 工时和范围的计算方式

100 小时是排程假设，不是你的工作承诺。每周结束记录实际主导工时、辅助工时、Agent 使用成本或额度、已完成可玩结果、阻塞。比较最近两周真实产出，再决定下周范围。

| 实际可用主导工时 | 建议范围 | 优先保住 |
| --- | --- | --- |
| 少于约 50–60 小时 | 必须尽早收缩成极小课程版：约 6 种怪、2 组羁绊、2 场短挑战、同地图复用 | 商店构筑、部署策略、技能、完整胜负与重开；不承诺此工时一定足够 |
| 约 100 小时 | 基础目标：8 种怪、3 组羁绊、3 场挑战、1 个地图模板 | 可读性、稳定性、两种以上进攻办法、第二台电脑可运行 |
| 约 150–200 小时 | 优先补试玩、引导、平衡、资源一致性，再考虑第二地图 | 每项扩展都有验收和回退点 |
| 更高投入 | 按已验证产能增加少量内容，最多向 GDD 扩展档靠拢 | 不因为 Agent 输出快而重写架构或堆卡量 |

工时不足时按顺序砍：额外地图 → 更多卡牌 / 特效 → 复杂羁绊 → 2× 加速等便利项。不能先砍错误反馈、重试、独立构建、验收测试或最后一周缓冲。若关键路径持续不达标，连基础目标也要减，而不是挪用全部测试时间。

## 3. 十周路线图

下表按相对周安排；没有正式截止日期，不擅自写死提交日。若某周少于预期工时，按照出口条件判断，不机械追赶功能数。

| 周 | 主导工时预算 | 本周目标 | 可查看结果 | 未达标时怎么处理 |
| --- | --- | --- | --- | --- |
| 1 | 8h | 环境、课程准备、关键规则与工程基线 | 可打开空工程 / 启动场景，首个可玩目标、Git 基线 | 不做美术；先解决工程运行与规则边界 |
| 2 | 12h | 固定路线、移动、阻挡、攻击、穿门 | 一个怪物能被阻挡、拆防守或穿门 | 只保留单路线与两类防守者 |
| 3 | 10h | 费用 / 次数 / 部署 CD / 首领技能 / 正确胜负 | 3 种怪的独立战斗原型与重试 | 若策略价值不成立，先修战斗，后续内容减档 |
| 4 | 10h | 商店、金币、编队、升星 | 招募到开战的可操作界面 | 先确认等级/经验经济和商店规则，再拆单目标任务；利息仍未授权 |
| 5 | 10h | 多标签羁绊、关间流程、完整小闭环 | 6 种怪、2 场，玩完可重开 | 若未闭环，锁定 6 怪最小范围，停止扩卡 |
| 6 | 10h | 形成第二种打法、引导与反馈 | 新玩家看得懂卡牌和失败原因 | 复用地图，优先修误解，不堆新单位 |
| 7 | 10h | 基础内容补齐、第一次外部试玩 | 最多 8 怪、3 场、3 羁绊及问题清单 | 缩到已成立的数量；周末冻结新增大机制 |
| 8 | 10h | 按试玩修体验、统一美术音效、性能排查 | 功能冻结后的 Beta 构建 | 新想法进待办，不继续改成长循环 |
| 9 | 10h | 回归、干净工程、第二台电脑、答辩材料 | 发布候选包 RC1、测试记录、演示录像 | 有阻断故障就修；删除高风险非必需内容 |
| 10 | 10h | 最终验收、打包、备份、演练与缓冲 | 提交包、源工程、说明、备用演示 | 只修阻断 / 严重故障，不升级依赖或重构 |
| 合计 | 100h | 70h 建立与完善，30h 试玩后打磨 / 验收 / 缓冲 | 每周都有可检查版本 | 辅助者工时不算入这 100h |

### 第 1 周：让后面每次工作都可恢复

先做一次 30 分钟范围会议，确认 GDD 的 D01–D06 可作为哪些原型假设、谁负责最终决定、辅助成员实际每周能做什么。平台和 2D 视角尚未确认时先写建议值；不要将建议升格成承诺。课程已允许 Unity，无须再次争论引擎。

新项目建议选择团队机器可用、目标平台支持的 Unity 6.3 LTS 稳定补丁，**先检查现有安装和包兼容，再记录精确版本**；若学校已有要求或团队已有兼容环境，优先沿用已验证版本。官方支持页当前列出 6.3 LTS 支持至 2027 年 12 月。本项目选择锁定版是为了课程周期内减少变更，并不等于所有新项目只能用 LTS。[Unity 支持说明](https://unity.com/releases/unity-6/support)

准备以下基线：

1. Unity Hub 可打开项目，入口场景已保存，有一个明确开始入口。
2. 保留 `Assets`、`Packages`、`ProjectSettings`；保留资源对应 `.meta`，忽略 `Library`、`Temp`、`Logs` 和本地构建产物。提交 `manifest.json`、`packages-lock.json` 与 `ProjectVersion.txt`。
3. 使用可见 `.meta` 和文本序列化；资源移动优先在 Unity 内完成，不重建已有 GUID。[版本控制设置](https://docs.unity3d.com/6000.0/Documentation/Manual/class-VersionControlSettings.html)、[文本序列化](https://docs.unity3d.com/6000.0/Documentation/Manual/class-EditorManager.html)
4. 第一次提交和可恢复备份；从副本打开检查，不以“文件夹看起来齐全”代替恢复验证。
5. 尽早导出一个最小 Windows 包确认构建链，不等游戏全做完再首次打包。目标平台未确认时标注这是试验构建。
6. 放入简短 `AGENTS.md` 与文档入口，记录真实工程路径、精确版本、入口场景、测试入口和未实现功能。

你学习 Console、Inspector、Prefab、Git 差异；辅助 A 负责整理课程准备材料和现场提问；辅助 B 记录引擎、启动步骤、首次运行截图与一段真实 AI 核验过程。

出口：别人按说明能打开工程；若仍是空工程，明确写“尚未实现玩法”。参考附件本就不要求课前完成原型，不需要制造虚假进度。

### 第 2–3 周：先证明一场战斗值得做

按依赖顺序实现：路线与生命 → 防守攻击 / 阻挡 → 穿门 → 资源部署 → 首领技能 → 结束判定 → 重试。先固定编队，不接商店；先让功能有可读状态，再加动画。

第 2 周必须可观察怪物位置、血量、阻挡关系和门的变化；第 3 周必须能比较部署顺序与技能时机。首领至少展示一次“技能 CD 与部署 CD 分开”，并有多首领共存的开发测试场景，防止实现暗含单首领假设。

为同一配置录两次：一次随手部署，一次解释部署间隔和技能时机。用剩余门防御、穿门单位、技能命中 / 回费量说明差异。此时不要求漂亮，但玩家输入要改变结果。

你负责每天一轮 5–10 分钟实玩并决定体验；辅助 A 按步骤找资源耗尽 / 冷却 / 暂停的边界；辅助 B 保留录像、场景配置 ID、运行版本与结果。Agent 负责逻辑、单元测试、配置与调试显示。

出口：3 怪、两类防守、无自然回费、费用 / 次数 / 两套 CD、蓝门差异伤害、正确胜负、重试都能运行；GDD 边界例通过。若策略差异没有出现，调整阻挡、单位职责或技能窗口，后移商店并减少后续内容。

### 第 4–5 周：接通构筑，不让 UI 吞掉整个项目

金币先独立于 DP，实现购买 / 售出 / 刷新和固定编队，再做同卡合成与多标签羁绊。每接入一项，就回到同一战斗检查结果，不连续两周只写界面。

羁绊先用三个 ID 和明确效果，不先做几十种通用效果编辑器。准备一个确定的多羁绊示例和一个重复同名卡示例，检查“种类去重”是否符合决定。合成要覆盖编队卡 / 备战卡混合、备战满、金币恰好够的事务边界。

保存关间进度，并保留开战快照供重试；不用先实现战斗中保存。只有保存字段和版本真的被实现后，才写“支持继续挑战”。完整小闭环至少包含两场、关间金币结算、最后胜利和新挑战。

你判断商店每次选择是否有意义；辅助 A 检查买卖与升星、记录可重现漏洞；辅助 B 测试启动到结算的完整路径、核对 UI 文本和配置。Agent 分离经济状态与战斗状态，补集成验证。

出口：6 怪 + 简单商店 + 升星 + 多羁绊 + 两场挑战 + 重开。若第 5 周仍未完整走通，立刻宣布进入最小范围，停止扩单位、地图和技能类别。

### 第 6–7 周：让别人不用你讲也能玩

优先处理三种误解：不知道为何不能部署、不知道首领技能对应谁、不知道为何失败。用卡牌禁用原因、羁绊预览、路线 / 范围提示与结算说明解决；不要用长篇教程代替反馈。

内容扩充以差异为依据：新卡是否增加一种进攻办法？新防守配置是否要求重新安排顺序？若只是血量更高，先复用已有单位。基础目标最多 8 怪、3 场、3 组羁绊，达到最小闭环即可视工时少做。

邀请 3–5 名未参与设计的人，各玩一轮。第一次尽量不口头指导，记录卡住的位置；之后再问“为什么这样选”“失败后下一次会改什么”“想不想再试”。保留原始观察，勿将礼貌评价写成“好玩已验证”。

你整理最影响体验的前三个问题并排序；辅助 A 主持试玩、记录玩家行为；辅助 B 管理资源目录、中文字体、音量与视频。辅助者可用 Agent 处理自己的任务，但需要理解并展示实际产物。

出口：一组相同预算下的不同打法、能看懂的技能窗口、清晰失败原因、一次外部试玩记录。第 7 周末冻结新大机制，后续只调整参数、补反馈、修问题和完成已承诺内容。

### 第 8 周：性能与表现一起服从可读性

统一怪物大小、颜色 / 形状身份、卡牌排版、按钮状态、技能表现与音效层级。避免同时播放大量高亮导致看不见路径。低成本单位也要能一眼区分。不要用高级资源替换造成尺寸、碰撞、动画事件全量返工。

在实际压力配置下记录帧耗时、峰值实体数和卡顿来源，先修明显重复分配、每帧全局搜索、重复生成与销毁。只在证据支持时加入对象池或局部优化；不把“优化”当成改 ECS 的理由。检查暂停恢复、失焦、窗口缩放、中文缺字、音量保存和反复重试。

出口：Beta 包能完整玩完；改过的模块重新通过相关检查；每项性能结论有设备、场景和测量方式。若尚有严重功能缺口，优先修复，表现降档。

### 第 9–10 周：把工程变成可靠交付

第 9 周从干净副本 / 克隆打开，执行既定测试和打包，另一台电脑离线启动发布包并完成挑战。检查漏资源、大小写路径、缺字体、依赖编辑器的代码、存档路径和声音设备差异。

形成 RC1，记录提交版本、引擎版本、构建时间、目标平台、内容清单、已知问题、测试结果和文件校验值。每次 RC 修改都重新跑受影响检查与完整流程，不用“上次测过”覆盖新包。

第 10 周保留足够空白处理机器故障和临时问题。准备源工程、发布包、启动说明、2–3 分钟演示录像、分工记录、AI 使用与人工核验证据、已知限制。现场无法运行时有离线录像，但录像不能伪装成实时运行。

你必须能用 3–5 分钟解释核心循环、两个具体规则、一次 Agent 错误与自己的核验、三人真实贡献。两名辅助成员也分别说明自己的工作。完成一次恢复演练：在另一个目录重建与启动，不能只把压缩包复制两遍。

出口：发布包与源工程一一对应，第二台电脑验证通过，材料和备份齐备。最后一周不升级 Unity、不换 UI 框架、不加新稀有度和新成长系统。

## 4. 两名辅助成员的可交付分工

| 角色 | 稳定职责 | 每周交付 | 验收方式 |
| --- | --- | --- | --- |
| 你：产品 / 集成负责人 | 规则决定、关键玩法、合入、构建、体验取舍 | 可玩版本、三条本周结论、下周范围 | 实玩并解释改动的因果 |
| 辅助 A：测试 / 玩家观察 | 按用例跑流程、复现问题、主持试玩、收集反馈 | 问题卡 + 录像 / 截图 + 环境信息 | 另一人能用步骤复现，能说明问题对体验的影响 |
| 辅助 B：内容 / 交付 | 受控配置、资源命名与来源、文本核对、演示材料、第二机检查 | 数据改动表 / 来源台账 / 测试包记录 | 配置校验通过、实际游戏效果一致 |

他们不需要先成为程序员，也不应该被写成没有产物的“杂活”。第一次只各分配一个有清晰完成条件的任务。若某成员未承诺工时，由你准备可替代的小任务，不让其工作卡住主线。

## 5. Agent 工作方式：先少量串行，再有限并行

### 5.1 四种职责，不等于必须同时开四个 Agent

**需求拆解者**把本周目标拆成半天内可验证的任务，列状态与反例。**实现者**只完成选定任务及必要相关修复。**审查者**根据 GDD 和差异找错，不以实现者摘要代替阅读。**验证者**运行测试、Unity 或发布包，报告证据与未运行项。

前 3 周建议一个实现会话 + 一次独立审查，顺序执行即可；后面接口稳定后，可让两个互不改同一文件的任务并行。不要同时让多个写入者编辑同一个 Unity 场景、Prefab、配置资产或包清单。

审查 Agent 也会漏错。关键结果至少要有可运行的反例测试或人类实玩，不能靠两个 Agent 互相说“看起来正确”。

### 5.2 需要任务卡时可参考的内容

```text
任务编号 / 标题：
玩家可感知的目标：
规则依据：GDD 的具体编号、状态是已定还是试验建议
前置版本 / 输入状态：
允许修改的模块与唯一写入者：
明确排除的扩展：
示例与反例：
验收：输入 → 行为 → 可观察结果
验证：自动测试、Unity 操作、构建检查分别是什么
交付：改动说明、真实结果、未运行项、恢复方法
```

任务宜控制为约 1–3 小时人工可验收的工作片段；时间更长就按玩家行为拆，不按类文件数量拆。不要把“整个战斗系统”扔给一次会话后等它自证完成。

### 5.3 日常闭环

1. **读事实：** 读取当前任务、GDD 对应段、项目指令、相关代码和 Git 状态；先知道别人的未提交改动。
2. **定边界：** 对小任务用数行说明改什么、如何验证，随后继续做；不每一步都等待人类批准。遇到真正改变核心规则的决定，先记录选项，同时推进不依赖该决定的工作。
3. **实现：** 先做小的端到端行为；保留稳定 ID 与资源引用；不顺手重写无关模块。
4. **运行：** 先编译，再跑有意义的规则 / 集成测试，再由人实际操作受影响交互。仅有静态阅读时明说未运行。
5. **审查：** 独立会话查看变更与规则，优先检查失败路径、资源事务、暂停和重试，不追求风格性重写。
6. **集成：** 在主集成工程运行，按现有授权提交 / 合入；本地快照用于恢复，远端推送和公开发布按真实任务权限处理。
7. **留记录：** 简短记录版本、做成什么、证据、遗留问题与下一步，不复制全部聊天。

新会话开始时读取 `STATUS`、当前任务和相关规则；会话结束时更新真实进度。摘要不得写“全部完成”而省略没有跑过的构建。

### 5.5 Unity 并行工作的特殊约束

并行工作可采用独立 Git worktree：它提供独立检出目录，需要 Git 仓库；它不会替代接口设计、文件责任和最终集成验证。[OpenAI 官方 worktree 文档](https://learn.chatgpt.com/docs/environments/git-worktrees)

本项目建议只保留一个由负责人维护的 Unity 集成编辑器，逻辑 / 测试任务在独立目录工作；同一路径不同时让编辑器和自动化写场景。其他 worktree 如需真正运行 Unity，要单独建立自身缓存并检查资源和机器条件，不能只因为文件被合并就宣称跑过。

可并行的例子：A 写普通 C# 费用 / 次数规则及测试；B 只读审查既有技能代码；C 整理来源台账。不可并行的例子：A 和 B 同改战斗 Scene；A 改 UnitDefinition 字段而 B 尚按旧字段生成全部配置；多人各自更改包依赖。

先稳定接口再分任务；接口变化由一个负责人完成并通知依赖任务。共享文件有唯一写入者。合并先处理代码编译，再校验资产和场景引用，再运行整场。合并冲突不能简单保留某一侧整份 YAML。

资源结构变动优先使用幂等 Unity Editor 工具：重复执行不会复制资产、改变已有 GUID 或重置人工配置。工具必须可读地报告创建 / 更新 / 跳过项；需要 Unity 执行的步骤没有执行就不能称已完成。直接编辑文本场景时需极小范围、明确引用并立即验证，不大规模手写序列化文件。

### 5.6 Agent 卡住时怎样处理

- 连续两次修复没有改善：停止扩大改动，保留第一条错误和最小复现，检查版本 / 引用 / 状态假设。
- 一次改动引发大量编译错误：先找最早公共接口错误，不让 Agent 对每条报错分别打补丁。
- 场景可开但按钮没效果：检查引用、事件绑定、输入状态与是否在正确入口，不只阅读 C#。
- 测试绿但游戏错：区分逻辑测试与 Unity 绑定，补能触发真实问题的用例或 Play Mode 测试。
- Agent 建议更换技术栈：要求它给出当前阻塞证据、最小修复和迁移成本；不因一次工具报错重开项目。
- 额度 / 网络不可用：使用上一个可玩版本，人工跑测试、整理内容和试玩，不让编程会话成为所有任务的单点。

## 6. 技术方案：只做这款游戏需要的规模

建议普通 C# 保存规则状态，Unity 负责表现和输入；用 ScriptableObject 保存只读配置，运行状态单独创建。既能通过 Unity 编辑数据，也方便测试费用、合成和羁绊。UI 基础版可用熟悉的 uGUI + 中文字体方案，具体包版本在建项时锁定，不同时维护两套 UI。

不预设大型事件总线、依赖注入框架、通用技能脚本语言、动态寻路、联网同步和 ECS。固定路径先用路径进度 + 逻辑阻挡；对象池按测量决定何时做。跨模块只传需要的数据和事件，不让 UI 直接修改金币、DP 和技能冷却。

建议最少状态机：挑战准备 → 战斗 → 本场结算 → 下一场准备 / 最终结束。战斗状态内有运行 / 暂停 / 已结束，结束事件幂等。经济操作使用事务，重试恢复开战快照。创建存档版本号，坏档保留备份并提示重新挑战，不用异常后悄悄生成一份看似正常的旧进度。

## 7. 质量保障：测会损坏体验的行为

### 7.1 五层检查及证据

| 层级 | 检查对象 | 主要执行者 | 证据 |
| --- | --- | --- | --- |
| 配置 / 静态 | ID、引用、数值范围、概率、路线、资产缺失 | Agent 工具 + 集成负责人 | 校验结果与错误定位 |
| Edit Mode | 扣费事务、次数、CD、合成、羁绊、胜负边界 | Agent 实现 / 独立审查 | 实际测试输出、运行时间、版本 |
| Play Mode | 场景绑定、生成、阻挡释放、按钮、暂停、重试 | Agent 能运行则运行，负责人复核 | 测试结果 + 实际运行 |
| 发布包 | 从启动到结算、离线、字体、输入、存档、性能 | 辅助 A/B + 负责人 | 平台 / 机器 / 包版本 / 录像 |
| 体验 | 是否理解、有没有选择、愿不愿意再试 | 外部试玩者，辅助记录 | 原始行为观察和下一次修改假设 |

Unity Test Framework 支持 Edit Mode、Play Mode 及目标平台测试；具体使用项目已安装的兼容包版本，不照抄网页包版本号升级。[Unity 测试框架说明](https://docs.unity3d.com/Packages/com.unity.test-framework@1.4/manual/index.html)

### 7.2 第一批有价值的测试

1. 费用正好够的成功部署只扣一次，失败不改变任何资源；费用永不为负。
2. 次数耗尽和冷却未完成分别拒绝；同帧两次提交不会越过校验。
3. 暂停期间移动 / 攻击 / 两套 CD / 回费均停止，恢复继续。
4. DP=0 但怪物在场不失败；空场、无任何未来机会才失败。
5. 不同首领实体技能独立，一个死亡不会清空另一个的 CD 或头像绑定。
6. 同种重复卡不重复贡献羁绊；多标签同时贡献；备战不计数；开战快照不被商店改动。
7. 三合一、满备战、买卖与金币变化原子完成，不丢卡、不复制金币。
8. 同一实体穿门只扣一次；胜利不会被随后资源判负覆盖；奖励幂等。
9. 重试清理旧事件、旧单位、阻挡、对象池状态和监听，连续重试不残留。
10. 相同版本、种子和操作序列结果稳定；不同测试不共享被修改的配置资产。

不为每个显示属性写镜像测试，也不以代码覆盖率代替玩法验证。低影响可逆文本调整可人工核对；金币、部署、判负、资源引用等错误会破坏整场，值得自动化。

### 7.3 每次任务、每日和每周

任务完成：编译 + 相关用例 + 受影响交互；涉及场景引用必须进 Unity。每天有代码合入时，跑一次小烟雾：启动、部署、技能、穿门、胜负、重试。每周出一个可运行构建并完整玩一轮。重复检查以变更和风险为依据，不在同版本无新信息时反复跑全套浪费时间。

到第 8 周起维护固定回归集：普通阵容、弱阵容、强阵容、双首领、次数耗尽、暂停恢复、连续重试、损坏存档。功能冻结后仍要测完整流程，不能只测最后修的按钮。

### 7.4 问题分级和修复原则

| 级别 | 例子 | 行动 |
| --- | --- | --- |
| S0 阻断 | 无法启动、无法完成流程、存档不可恢复、持续崩溃 | 停止新功能，优先修复 / 回退 |
| S1 严重 | 复制资源、误判失败、首领技能打错实体、关卡死局 | 发布前必须处理 |
| S2 体验 | 文字误导、主要策略难理解、频繁无意义等待 | 依影响排序，重点修前三项 |
| S3 打磨 | 非关键动画、边缘布局、可接受表现瑕疵 | 有余量再做，记录已知限制 |

问题卡包含：包 / 提交版本、设备、场景 / 种子、前置存档、操作步骤、预期 / 实际、录像、严重度。修复一个问题后保留其最小复现作为回归资产。

### 7.5 让“好玩”也能迭代

每轮只检验一个具体猜想，例如“玩家等 CD 太久是因为可选卡太少”或“首领技能反馈不明显导致玩家忘记用”。先记录现象，再改一项关键变量；不要同轮同时改商店概率、费用、血量和地图位置，导致无法判断原因。

建议关注：是否尝试第二套组合、失败后能否说出一个改法、技能是否改变进攻窗口、强阵容是否顺畅、弱阵容是否仍有操作空间。通关时间可以衡量拖沓，但不能据此加倒计时违背既定目标。
